# Выбор этапов

Владелец решает, какие этапы идут в прогон, кто их исполняет и сколько это стоит. Ты показываешь всё, что есть, и рекомендуешь. Приоритеты рекомендации по убыванию: не оставить проблем, экономия, время.

## Откуда этапы

**В BB.** Этапы и их исполнители перечислены в инструкциях хода, в порядке flow. Шлёшь все, ни одного не пропуская и не переставляя. Тред, созданный с «Автоматически», сначала получает flow: агент выбирает его по описаниям flow из инструкций хода.

**В Claude Code.** Списка flow и инструмента выбора flow здесь нет — этапы по шагам работы владельца: задача, прототип, спецификация, план, реализация, тестирование, ревью, демонстрация. Тестирование идёт до ревью: прогон дешёвый, а ревью на красной базе не снимается.

Шаг, который этой задаче не нужен, показываешь нерекомендованным, а не выбрасываешь. Задача нужна всегда, кроме правки в три строки без риска; прототип нужен, когда не очевидно, как оно будет выглядеть; спецификация — когда меняются логические узлы: появляется или исчезает часть, зависимость, стык; план — когда работу исполняешь не ты.

## Что про каждый этап

- Состояние: сделан — со ссылками на результат, не сделан — с рекомендацией брать или не брать.
- Исполнитель: сам или один из исполнителей этапа — агент, workflow. Рекомендуешь того, кто окупается, по правилу ниже.
- Цена: доля объёма в процентах и риск, у исполнителя — множитель. Доля этапа — по истории похожих задач; истории нет — скажи, что цифра грубая. Доля — только работа сверх пунктов Definition of Done: проверки, уже посчитанные в пункте, второй раз не считаются.

## Кем исполнять — окупается ли граница

Граница между агентами стоит фиксированную цену: исполнитель заново читает файлы и заново въезжает в задачу. Возвращает она выигрыш, который растёт с объёмом работы за границей. Вопрос всегда один: **работа за границей больше, чем въезд в неё?** Больше — отдаёшь. Меньше — делаешь сам.

Три источника выигрыша, каждый работает сам по себе; чем больше их совпало, тем раньше окупается граница:

1. **Изоляция контекста.** Главный агент платит за весь префикс на каждом ходу: через двадцать ходов он двадцать раз оплачивает разбор, сделанный в начале. Субагент стартует с чистого листа и держит только своё задание.
2. **Модель под роль.** Реализация на Sonnet, ревью на Opus только для чтения, прогон тестов на Haiku. Главный агент на дорогой модели платит её ставку за всё подряд, включая чтение файлов и запуск тестов.
3. **Независимость проверки.** Проверяющий не видел, как писался код, поэтому проверяет результат, а не замысел. Это не экономия, а требование: на любой правке, где решение принимал ты или субагент, результат проверяет не автор.

| Что за работа | Чем исполнять |
| --- | --- |
| Правка в одном месте; ответ на вопрос; чтение и разведка на пару файлов | Сам. Объяснить дороже, чем сделать |
| Широкий поиск по репозиторию, где нужен вывод, а не дампы файлов | Один субагент-разведчик только на чтение, одно взаимодействие |
| Работа на несколько файлов, но в один заход, без циклов | Сам; ревью и приёмку ведёт отдельный проверяющий |
| Работа в несколько циклов «сделал — проверили — поправил», даже одной группой | Конвейер: реализация → прогон → ревью; красный прогон возвращает в реализацию, не дойдя до ревью. Изоляция контекста и модель под роль окупают границу без всякого параллелизма |
| Работа делится на группы, не пересекающиеся по файлам | Тот же конвейер, группы параллельно. Параллелизм ускоряет, но не он делает конвейер выгодным |

Тема работы способ не задаёт. «Это программирование логики, значит нужен конвейер» — неверно: конвейер окупает объём и число циклов, а не предмет.

**Workflow.** Конвейер выбран — смотришь, есть ли готовый среди исполнителей этапа или в `~/.claude/workflows/`. Есть — называешь владельцу по имени и говоришь, из чего он состоит. Нет — два варианта с оценкой: собрать новый или вести те же стадии вручную, вызывая субагентов по одному. Ручные стадии дают тот же выигрыш от изоляции и моделей; workflow добавляет повторяемость, параллельные группы и возобновление с середины. На одной группе в два-три цикла разница невелика — не заводи workflow ради самого workflow.

**Навыки и права — до запуска.** Прежде чем рекомендовать исполнителя, назови, какие навыки нужны его работе, и проверь, что файлы на месте; пишущему субагенту нужен свой worktree, читающему — нет; тому, кто ходит в сеть, — работа вне песочницы. Навыка нет — скажи владельцу, какого и что без него будет хуже, и предложи три выхода: работать без него, подождать, завести его отдельной задачей. Сам не выбираешь.

## Как спросить

**В BB.** Этапы — в `setup.stages` того же брифа `ask_decision`, что Вопросы и Definition of Done, — все этапы flow, в его порядке, с id из инструкций хода:

| Поле | Что это |
| --- | --- |
| `id`, `state` | Id этапа из flow; `todo` — не сделан, `done` — сделан. Пройденные этапы — `done`, из прогона их не убрать |
| `results` | Только у сделанного этапа навыка: `[{ label, target }]`. `label` — имя файла из `target` (с расширением или без, например `spec.md`) или ключ задачи вроде `BP-28`, а не заголовок документа; `target` — путь от корня worktree, абсолютный путь или URL. У встроенных и `todo` этапов их нет |
| `recommended` | `true` — ты рекомендуешь взять `todo` этап в прогон |
| `executor` | `self` или id одного из исполнителей этапа из инструкций хода |
| `share` | `{ percent, risk }` у каждого `todo` этапа навыка: его доля объёма и как он меняет риск |
| `factors` | `{ <id исполнителя>: { factor, risk } }` — множитель и риск каждого исполнителя этапа |

Ни `add`, ни `adds` на этапе, ни полей старых брифов — `artifacts`, объектов `executor` и `checker`, `testing`, `budgetTarget`, `budgetMax`, состояния `review`: их заменили этапы, а кнопка «Бюджет» складывает прогноз сама.

**Этап — доля объёма.** `share.percent` — сколько этап стоит сверх пунктов Definition of Done; проверки, уже посчитанные в пункте, второй раз не считаются: этап, который делает саму работу, — 100, спецификация около 15, ревью около 20, задача или демонстрация около 5. Исполнитель в `factors` умножает долю этапа: субагент на модели дешевле — меньше 1, workflow с лишними проверками — больше 1, всегда больше нуля; ты сам — 1. Плагин считает доллары и минуты: объём — пункты Definition of Done, оценённые по `flow-criteria`, — идёт один раз, а этап в прогоне добавляет сверху объём × percent × factor. Этап самой работы и есть этот объём: тобой он ничего не добавляет, другим исполнителем — только (factor − 1) × объём. Бриф до запуска с `todo` этапом навыка без `share` или с прогнозом $0 / 0 мин инструмент не примет. Весь прогноз ложится в полосу закрытых задач той же оценки (якорь — в `flow-criteria`); прогноз выше неё требует причины, названной во вступлении.

**Риск этапа** — как этап меняет риск всей работы, а не сколько может сломаться внутри него. 1r ≈ 10% шанса, что блокирующий дефект дойдёт до владельца. Повышает его только реализация, и её риск идёт на пункты Definition of Done, разложенный по ним, — этап самой работы шлёт `share.risk` 0, плагин его не считает; спецификация, план, прототип, ревью и тестирование его снижают; вопросы, Definition of Done, выбор этапов, демонстрации, автоматизации и этапы-действия — 0. Проверка с плюсом делает пропуск проверок на вид безопаснее — такой не шли. Шкала:

| Этап | Риск | На чём стоит число |
| --- | --- | --- |
| Реализация, в сумме по пунктам | xs +1, s +3, m +5, l +6 | Замерено: первое ревью нашло блокирующие дефекты в 43 из 83 закрытых задач с вердиктом — s 3 из 10, m 17 из 33, l 22 из 37. У xs ревьюенных задач нет, +1 — оценка |
| Ревью другим агентом | Около минус того, что добавила реализация (m −5, l −6) | Замерено теми же числами: эти дефекты поймало ревью, а не владелец. Ревью самим собой — половина, не замерено |
| Тестирование, тесты до кода | −1…−2 | Оценка, не замерено |
| Спецификация | −1 | Оценка, не замерено: задачи со спецификацией не прошли первое ревью в 7 из 15, без неё — в 36 из 68, разница в пределах шума. Спецификация в основном спасает от неверного направления, а его вердикт ревью не считает |
| План | −1 | Оценка, не замерено: все 6 задач с планом всё равно не прошли первое ревью — план ревью не заменяет |
| Прототип | −1, когда вид не очевиден, иначе 0 | Оценка, не замерено |

Для правки меньше или больше своей оценки сдвигайся по шкале и называй причину во вступлении. Пересчитывай замеренные строки по `docs/tasks/done/`, когда история растёт: задачи с `SATISFIED` в комментариях, доля с `NOT SATISFIED` по `estimate`.

**Что видит владелец.** Виджет пишет цену мелко, как «+$2–4 –2r +20 мин» (часть без изменения опускается; плюс риска красный, минус зелёный), рядом с базой Definition of Done, на кнопке этапа — для выбранного исполнителя — и у исполнителей в раскрытом списке разницей с тобой, а этапы прогона складывает в кнопку «Бюджет · цель · до потолка» — никогда не ниже нуля; уже потраченное на тред в итог не входит — с разбивкой по столбцам время, риск, цель, потолок. Вторая строка кнопки — плановое время работы. Ответ несёт строку «Бюджет — прогноз $18 · до $31, риск +2, время +40 мин» или «Бюджет — своя цена $25 · до $40 (прогноз …)». Время, уже потраченное на планирование, плагин добавляет сам первой строкой разбивки с пометкой «уже потрачено», только для справки; не присылай его. Твоя рекомендация предвыбрана на кнопке этапа — в прогоне или нет и исполнитель, — и владелец меняет только то, с чем не согласен; ✦ рекомендации он видит в раскрытом списке. Если в прошлом отвеченном брифе треда владелец сам выбрал исполнителя этапа, плагин ставит этот выбор вместо твоей рекомендации. Рекомендуй как обычно.

После запуска инструмент принимает `setup.stages`, только пока этап выбора этапов или Definition of Done ещё `todo`; бриф без `setup.stages` в запущенном треде бюджета не показывает.

```json
{
  "title": "CEL-115 — дерево в DevShell",
  "kind": "brief",
  "setup": {
    "stages": [
      { "id": "questions", "state": "todo" },
      { "id": "criteria", "state": "todo" },
      { "id": "select", "state": "todo" },
      { "id": "task", "state": "done", "results": [{ "label": "CEL-115", "target": "docs/tasks/in_progress/cel-115.md" }] },
      { "id": "prototype", "state": "done", "results": [{ "label": "prototype.html", "target": "docs/assets/cel-115/prototype.html" }] },
      { "id": "demo", "state": "done" },
      { "id": "spec", "state": "todo", "recommended": true, "share": { "percent": 15, "risk": -1 } },
      { "id": "plan", "state": "todo", "recommended": true, "executor": "agent:planner", "share": { "percent": 10, "risk": -1 }, "factors": { "agent:planner": { "factor": 0.8, "risk": 0 } } },
      { "id": "implement", "state": "todo", "recommended": true, "share": { "percent": 100, "risk": 0 } },
      { "id": "review", "state": "todo", "recommended": true, "executor": "agent:reviewer", "share": { "percent": 20, "risk": -2 }, "factors": { "agent:reviewer": { "factor": 1.2, "risk": -3 } } },
      { "id": "testing", "state": "todo", "recommended": true, "share": { "percent": 5, "risk": -2 } },
      { "id": "demo-2", "state": "todo", "recommended": true }
    ]
  }
}
```

Этапы — полный flow: вопросы, Definition of Done, выбор этапов, задача, HTML-прототип, демонстрация, спецификация, план, реализация, ревью, тестирование и вторая демонстрация; владелец добавил плану исполнителя `agent:planner`, а ревью — `agent:reviewer`. На объёме 17 минут из примера `flow-criteria` с рекомендованным ответом развилки этапы прогона добавляют 17 × (0,15 + 0,10 × 0,8 + 0,20 × 1,2 + 0,05) ≈ 9 минут. Порядок — flow этого владельца, а не рекомендация; этапы владельца могут быть другими — бери их из инструкций хода.

**В Claude Code.** Сделанные этапы — строкой в ответе со ссылками. Затем вопрос с `multiSelect: true` «Какие этапы взять в прогон?»: рекомендованные этапы первыми с «(Recommended)», в описании — цена и минуты; итог рекомендованного набора — в тексте вопроса. Вариантов больше четырёх — этапы группируются по порядку: «Спецификация и план», «Реализация и ревью». Там, где у этапа есть выбор исполнителя, — второй вопрос «Кто исполняет <этап>?» с разницей цены у каждого варианта.

Нет AskUserQuestion — таблица этапов в ответе — этап, состояние, рекомендация, исполнитель, цена — и просьба ответить, и ход заканчивается.

## После ответа

Идёшь по выбранным этапам в порядке flow. На этапе Демонстрация останавливаешься и показываешь сделанное. Остальное — до конца без новых вопросов, если не стало неясно, как действовать. Выбор владельца, отличный от рекомендации, не оспариваешь; его цену называешь в отчёте одной строкой, если она изменилась.
