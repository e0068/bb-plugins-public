# @bb-plugins/automation-steps

Шаги набора Pull Request, которые исполняют и Automations (`bb-plugin-automations-builder`), и Flow: закоммитить правки дерева (`git.commit`, чистое дерево — не провал, окружение без git — провал с папкой окружения и подсказкой направить проект на папку репозитория), подтянуть ветку к main, открыть PR без push, перевести связанные задачи в `in_review` и `done`, поднять версии затронутых плагинов разрядом (`files.bump-major`, `files.bump-minor`, `files.bump-patch`), смёрджить PR, подтянуть локальный main, перевести затронутые плагины bb на смёрдженный код (`bb.reinstall`), архивировать тред.

| Слой | Папка | Что внутри |
| --- | --- | --- |
| Ядро | [core/](core) | Чистые решения: базовая ветка, запросы GitHub, заголовок PR, видимость, готовность к мёрджу |
| Эффекты | [wiring/](wiring) | Клиенты GitHub, git и `bb` CLI за портами, проверяемые фейками |
| Помощники | [shell/pr-helpers.ts](shell/pr-helpers.ts) | Сборка шага из SDK, kv и настройки токена; Automations строит на них и состояние своих кнопок |
| Каталог | [catalog.ts](catalog.ts) | `STEP_IDS`, `STEP_LABELS`, `isStepId` — без импортов, их берёт и фронт |
| Шаги | [steps.ts](steps.ts) | `createSteps(ports)` — шаг по id отвечает `{ ok, detail }` или `{ ok: false, error }` и не бросает |

Нетестовый код импортирует только модули `node:` и файлы пакета: пакет собирается внутрь обоих плагинов, а сторонний импорт в `packages/` ломает установку из git. SDK берётся только типом, и тип этот подставляет плагин-потребитель через `paths` в своём `tsconfig.json` — у пакета своей копии SDK нет, иначе две копии типов расходятся. Обещание держит [architecture.test.ts](architecture.test.ts).

Шаг, упавший временно, повторяется сам — но только у того, кто берёт шаги через `createSteps`: повтор надет там. Automations собирает свою карту шагов из тех же помощников и повторов не имеет. Временная ошибка — `HTTP 5xx`, `429`, `408`, `404`, `409`, обрыв сети и `cannot lock ref` — проигранная гонка за git-ссылку, когда fetch соседнего треда сдвигает `origin/main` посреди нашего; всё остальное постоянная ([core/retry.ts](core/retry.ts)); паузы 2 и 8 секунд, то есть до трёх попыток. Успех не с первой попытки дописывает в строку шага `succeeded on attempt N`, окончательный провал — `(N attempts)`. Пауза приходит портом `sleep` в `StepPorts`: тесты подменяют её и не ждут ни секунды. Повтор безопасен потому, что шаг отвечает успехом на уже сделанную работу — открытие PR возвращает открытый PR ветки вместо второго, мёрдж отвечает `already merged` на влитый PR, бамп на ветке выше базы не пишет ничего.

Шаг «Смёрджить PR» (`git.merge`) сначала догоняет ветку открытого PR до ветки треда — `refreshOpenPr` в [shell/pr-helpers.ts](shell/pr-helpers.ts), тем же путём, каким «Открыть PR» обновляет найденный PR, — и только потом мёрджит. PR собран через API без пуша, поэтому коммиты, сделанные после «Открыть PR», иначе на GitHub не попадали и в main не уходили — так потерялись три коммита PR #685. Догнанный PR теряет коммит бампа, поэтому шаг бампа запоминает разряд в kv (`lastBumpKey`), а мёрдж после догоняния поднимает версию заново тем же разрядом; не поднялась — мёрджа нет. В строке шага догоняние названо (`MERGE_REFRESHED`). Незакоммиченное в дереве — отказ с причиной, а не мёрдж старого содержимого; открытого PR нет — мёрдж решает сам и PR не открывает. В тестах догоняние подменяется портом `refreshPr`.

Шаг «подтянуть ветку к main» (`git.fast-forward`, [wiring/catch-up.ts](wiring/catch-up.ts)) берёт вершину базовой ветки — той, от которой отведена ветка и в которую идёт PR: не отстаёт — успех без изменений, отстаёт без своих коммитов — перемотка, со своими — обычное слияние базы в ветку коммитом слияния. Конфликт только в файлах задач `docs/tasks/**` и в пунктах ченж-лога `bb-plugin-*/changelog/*.md` шаг сводит сам и коммитит слияние ([wiring/conflict-resolve.ts](wiring/conflict-resolve.ts), правило — [core/conflict-merge.ts](core/conflict-merge.ts)): у задачи, перенесённой одной стороной и правленной другой, папка из ветки (отмена в main побеждает), а задачу, перенесённую обеими сторонами, сводит агент; поля владельца и доски — `title`, `priority`, `due`, `labels`, `parent`, `key`, `epic` — из main, тело из ветки, комментарии обеих сторон по `id`, повторы ключей шапки, которые оставляет `merge=union`, схлопываются; у пункта ченж-лога файл с проставленной версией остаётся как есть, а новые заметки другой стороны уходят в `<слаг>-<n>.md` с `coming-soon`. Любой другой конфликт отменяет слияние целиком, называет файлы и приходит исполнителю полем `conflicts` провала (`CatchUpConflict` → `stepFailure` в [core/step-outcomes.ts](core/step-outcomes.ts)) — Flow по нему будит агента треда, а не повторяет шаг по таймеру. Стык проверен на настоящем git — [wiring/catch-up-resolve-git.test.ts](wiring/catch-up-resolve-git.test.ts). Незакоммиченные отслеживаемые правки — отказ до всякого слияния. Кнопка Fast Forward показывается по-прежнему только для чистой перемотки.

Шаг «выдать ключи задачам» (`bb.tasks-issue-keys`, [steps.ts](steps.ts)) зовёт `bb tasks keys issue` от имени треда и его проекта (`BB_THREAD_ID` и `BB_PROJECT_ID` — [core/bb-tasks-commands.ts](core/bb-tasks-commands.ts)) и коммитит дерево, если команда что-то вписала. Задача, рождённая в ветке, живёт без ключа, а правка из дерева треда его не выдаёт; команда Tasks+ даёт таким задачам следующие номера доски после наибольшего в ветке и в главном чекауте. Поэтому шаг ставят сразу после `git.fast-forward`: чем ближе он к мёрджу, тем меньше окно, в котором соседняя ветка возьмёт те же номера. Отказ команды — провал шага с её текстом, коммита нет.

Дочерний тред, чья база — ветка треда-родителя ([core/parent-delivery.ts](core/parent-delivery.ts)), сдаёт работу не на GitHub, а в дерево родителя: у ветки родителя нет копии на origin. `git.fast-forward` сверяется с ней на месте, без fetch; `git.create-pr` и `git.merge` вливают ветку треда в ветку родителя в его рабочей копии и отвечают «merged into …» или «already in …»; бамп, `git.pull-main` и `bb.reinstall` отвечают «not needed» — это дело PR родителя. Незаконченная операция в дереве родителя — отказ, конфликт отменяет слияние целиком и называет файлы. Остальные треды идут прежним путём. `git.merge`, влив ветку, говорит треду-родителю через порт `tell`, что волна у него: ветка, ветка родителя и её коммит ([`parentNote`](core/parent-delivery.ts)) — иначе агент родителя ищет PR в main; несказанное шаг не роняет, а называет в деталях. Решения — [child-thread-delivers-into-parent-branch](../../docs/decisions/child-thread-delivers-into-parent-branch.md), [parent-thread-told-of-delivered-wave](../../docs/decisions/parent-thread-told-of-delivered-wave.md).

Разошедшаяся ветка разбирается не одним слиянием. PR уезжает в базу синтетическим коммитом, собранным через API без push, поэтому локальная ветка предком базы не становится никогда, и слияние сводит её с её же изменениями, вернувшимися «с той стороны»: всё, что ветка тронула после мёрджа в тех же местах, конфликтует сама с собой. Поэтому у разошедшейся ветки сперва меряется содержимое. Целиком в базе — ветка доводится до базы, исход `reset-to-base`. Частично — ищется срез, самый свежий собственный коммит, чьё содержимое уже в базе ([wiring/merged-cutoff.ts](wiring/merged-cutoff.ts)), и на базу переносится только работа после среза через `git rebase --onto`, исход `replay-onto-base`. Среза нет — прежнее слияние. Конфликт переноса отменяется целиком и называет файлы, как и конфликт слияния; стык проверен на настоящем git — [wiring/catch-up-replay-git.test.ts](wiring/catch-up-replay-git.test.ts).

Шаг мёрджа спрашивает состояние PR у GitHub до попытки и после упавшей: влитый PR — успех шага (`already merged`), закрытый без мёрджа — названный отказ, ветка, которую GitHub считает конфликтующей, — названный конфликт вместо «HTTP 409». Окно, в котором GitHub пересчитывает mergeability, лечится повтором: 409 временный. Не смогли спросить GitHub — мёрдж всё равно пробуется, его делает сам bb.

Шаг бампа различает поломку и пробел. PR ещё не открыт или ветки нет на origin — это пробел (`gap` в [core/step-outcomes.ts](core/step-outcomes.ts)): шаг отвечает успехом и говорит, что версия поднимется бампом перед мёрджем. Цепочка на этом больше не встаёт — раньше вставала на первом же прогоне треда, чей flow ставил бамп до открытия PR.

Три шага бампа отличаются одним — разрядом: версия ставится не «на единицу от ветки», а на разряд от базовой ветки, какой она прямо сейчас ([core/merge-time-bump.ts](core/merge-time-bump.ts)), и коммитится в ветку открытого PR до мёрджа ([wiring/merge-time-bump.ts](wiring/merge-time-bump.ts)). Ветка, уже стоящая на цели, объявляется ahead: повтор прогона разряд не накручивает — поэтому цепочка ставит шаг и сразу за созданием PR, и перед мёрджем, где он в обычном случае не пишет ничего. Шагов бампа в цепочке нет — версия не растёт вовсе: другого механизма для неё не осталось. Тем же коммитом шаг ставит версию, дату и номер PR пунктам ченж-лога плагина — файлам `bb-plugin-<имя>/changelog/*.md` этого PR с `version: coming-soon` или с его же номером; PR без своего пункта получает `changelog/pr-<номер>.md` с заголовком PR ([core/changelog-entry.ts](core/changelog-entry.ts), [решение](../../docs/decisions/changelog-entry-file-per-pr.md)). Историю, которую PR добавляет, шаг не трогает: у неё нет номера этого PR. Появился в PR свой пункт — запасной `pr-<номер>.md` прошлого прогона удаляется. PR, который правит только `changelog/`, версию не поднимает. Дату шаг берёт сам — сегодняшний день по местному времени, одинаково для Flow и Automations.

Шаг `bb.reinstall` переводит на смёрдженный код каждый плагин, который PR задел; какие файлы он задел, спрашивается сравнением базы с веткой, а не берётся из локального main. Правка общего пакета `packages/<имя>` задевает и плагины, которые этот пакет собирают: шаг читает `git grep` в рабочей копии треда, какой код импортирует `@bb-plugins/<имя>` или `../packages/<имя>`, считая пакеты, подключённые через другие пакеты, и обновляет те из них, что уже установлены; тесты, конфиг vitest и README пакета в расчёт не идут ([core/package-consumers.ts](core/package-consumers.ts)). Граф не прочитан — шаг называет пакеты в ошибке, а плагины, которые PR задел напрямую, всё равно обновляет. Решение — [reinstall-reaches-package-consumers](../../docs/decisions/reinstall-reaches-package-consumers.md). Влит ли PR, шаг спрашивает у самого GitHub, а не у кэша bb — тот сразу после мёрджа ещё показывает PR открытым: пока GitHub отвечает живым PR на эту ветку, шаг отказывается работать, потому что обновление тянет плагин с базовой ветки и поставило бы код без этой ветки, отрапортовав «обновлено». Не 200 в ответе — это «не смогли спросить», а не «влит». Плагин, стоящий из другого источника — npm или git другого репозитория, — на месте не обновляется: шаг падает и называет его источник, потому что снос, который нужен для переезда, забрал бы настройки, секреты и расписания плагина. Плагин из локальной папки (`path:`) шаг оставляет как стоит и называет в строке успеха: такую установку владелец выбрал сам, и повтор её никогда не сдвинет. Плагин, ведущий прогон, не обновляется внутри цепочки — его id уходит в kv ключом `self-update-pending:<тред>` (и только когда шаг ответил успехом), а обновление применяет исполнитель после цепочки и только когда в процессе не осталось ни одного идущего прогона: bb выгружает плагин целиком, и обновление посреди чужой цепочки оборвало бы её.

Базовый режим (Origin или Local main) и кэш «уже влито» читаются из kv плагина-исполнителя: у Flow они свои, режим по умолчанию — Origin.

Тесты: `npm ci && ./node_modules/.bin/vitest run` вне песочницы.
