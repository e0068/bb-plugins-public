# @bb-plugins/automation-steps

Шаги набора Pull Request, которые исполняют и Automations (`bb-plugin-automations-builder`), и Flow: закоммитить правки дерева (`git.commit`, чистое дерево — не провал), подтянуть ветку к main, открыть PR без push, перевести связанные задачи в `in_review` и `done`, поднять версии затронутых плагинов разрядом (`files.bump-major`, `files.bump-minor`, `files.bump-patch`), смёрджить PR, подтянуть локальный main, перевести затронутые плагины bb на смёрдженный код (`bb.reinstall`), архивировать тред.

| Слой | Папка | Что внутри |
| --- | --- | --- |
| Ядро | [core/](core) | Чистые решения: базовая ветка, запросы GitHub, заголовок PR, видимость, готовность к мёрджу |
| Эффекты | [wiring/](wiring) | Клиенты GitHub, git и `bb` CLI за портами, проверяемые фейками |
| Помощники | [shell/pr-helpers.ts](shell/pr-helpers.ts) | Сборка шага из SDK, kv и настройки токена; Automations строит на них и состояние своих кнопок |
| Каталог | [catalog.ts](catalog.ts) | `STEP_IDS`, `STEP_LABELS`, `isStepId` — без импортов, их берёт и фронт |
| Шаги | [steps.ts](steps.ts) | `createSteps(ports)` — шаг по id отвечает `{ ok, detail }` или `{ ok: false, error }` и не бросает |

Нетестовый код импортирует только модули `node:` и файлы пакета: пакет собирается внутрь обоих плагинов, а сторонний импорт в `packages/` ломает установку из git. SDK берётся только типом, и тип этот подставляет плагин-потребитель через `paths` в своём `tsconfig.json` — у пакета своей копии SDK нет, иначе две копии типов расходятся. Обещание держит [architecture.test.ts](architecture.test.ts).

Шаг «подтянуть ветку к main» (`git.fast-forward`, [wiring/catch-up.ts](wiring/catch-up.ts)) берёт вершину базовой ветки — той, от которой отведена ветка и в которую идёт PR: не отстаёт — успех без изменений, отстаёт без своих коммитов — перемотка, со своими — обычное слияние базы в ветку коммитом слияния. Конфликт отменяет слияние целиком и называет файлы, незакоммиченные отслеживаемые правки — отказ до всякого слияния. Кнопка Fast Forward показывается по-прежнему только для чистой перемотки.

Три шага бампа отличаются одним — разрядом: версия ставится не «на единицу от ветки», а на разряд от базовой ветки, какой она прямо сейчас ([core/merge-time-bump.ts](core/merge-time-bump.ts)), и коммитится в ветку открытого PR до мёрджа ([wiring/merge-time-bump.ts](wiring/merge-time-bump.ts)). Ветка, уже стоящая на цели, объявляется ahead: повтор прогона разряд не накручивает. Шагов бампа в цепочке нет — версия растёт patch'ем в коммите PR, как раньше ([wiring/plugin-version-bump.ts](wiring/plugin-version-bump.ts)).

Шаг `bb.reinstall` переводит на смёрдженный код каждый плагин, который PR задел; какие файлы он задел, спрашивается сравнением базы с веткой, а не берётся из локального main. Влит ли PR, шаг спрашивает у самого GitHub, а не у кэша bb — тот сразу после мёрджа ещё показывает PR открытым: пока GitHub отвечает живым PR на эту ветку, шаг отказывается работать, потому что обновление тянет плагин с базовой ветки и поставило бы код без этой ветки, отрапортовав «обновлено». Не 200 в ответе — это «не смогли спросить», а не «влит». Плагин, стоящий из другого источника, на месте не обновляется — шаг падает и называет его источник: снос, который нужен для переезда, забрал бы настройки, секреты и расписания плагина. Плагин, ведущий прогон, не обновляется внутри цепочки — его id уходит в kv ключом `self-update-pending:<тред>` (и только когда шаг ответил успехом), а обновление применяет исполнитель после цепочки и только когда в процессе не осталось ни одного идущего прогона: bb выгружает плагин целиком, и обновление посреди чужой цепочки оборвало бы её.

Базовый режим (Origin или Local main) и кэш «уже влито» читаются из kv плагина-исполнителя: у Flow они свои, режим по умолчанию — Origin.

Тесты: `npm ci && ./node_modules/.bin/vitest run` вне песочницы.
