# Tasks+

> A fork of the Tasks plugin that keeps tasks as Markdown files on disk and adds native workflow fields — Type, Estimate, Check, time and budget.

## What it does

Tasks+ is a Linear-style tracker inside bb (plugin id `tasks-plus`) for planning work, delegating it to agents, and keeping the task record connected to the threads doing the work. It carries over everything the built-in Tasks plugin offers — projects and folders, task keys, statuses and priorities, labels (a board keeps the ones added in Manage → Labels with their colours even before a task carries them, [filesync/label-catalog.ts](filesync/label-catalog.ts)), subtasks, Markdown comments, attachments, agent presets and delegation, task mentions, and the full `bb tasks` CLI — and takes over that CLI name so it can replace the built-in plugin.

On top of that base it adds native fields for the project-memory workflow, editable in a task's detail rail: **Type** (epic, feature, bugfix, spike, refactor, migration, design), **Estimate** (xs, s, m, l, xl), **Check** (a multi-select of test, review, design, browser), **Planned Time** and **Actual Time** in whole minutes, and **Budget**, **Limit** and **Cost** in dollars to the cent. Type, Estimate, time and money are nullable — a task can be left unset, like `priority = none`.

An epic is an ordinary task typed epic. Sub-tasks nest to any depth, and a task belongs to the epic that is its nearest ancestor typed epic — whatever lies between, and a task's own type does nothing to its children. The board works that ancestor out when it reads the tasks ([shared/epic.ts](shared/epic.ts), `Task.epicId`); `bb tasks show` names it — the board has no Epic field, a task's place under an epic reads through Parent — and a task goes into an epic by taking the epic as its parent (the rail's Parent menu, `bb tasks update --epic <key>`). The older epic folders `<assignee>/<epic>/<status>/` are still read until `bb tasks epics migrate` turns each into an epic task and moves its files up beside it ([filesync/epic-migrate.ts](filesync/epic-migrate.ts)).

The other defining difference from the original is where tasks live: a task is a Markdown file in a status folder on disk, not a row in a database. Board metadata (folders, presets, saved views) is still kept in plugin storage, but the tasks themselves are read fresh from their files, and every edit made from the panel is committed and pushed to the board's git repository.

## How it works

The frontend registers four host slots in [app.tsx](app.tsx):

- `app.slots.navPanel` — the main **Tasks+** panel at path `tasks`, rendered by `TasksAppShell`, with an `experimental_sidebarAccessory` (`TasksSidebarAccessory`) for the sidebar footer. Navigation is a column of that panel, beside the area it navigates; on a narrow screen there is room for one, so the panel opens on the area and the topbar button brings navigation over the full width ([shell/columns.ts](shell/columns.ts)). Its `fixedTabs` add a **Task** tab to the page's right panel (`TaskSidePanelTab`): with Open in side panel on in a board's or table's Display panel, its cards or rows open there and the board or table stays in place; the choice belongs to that board or table and travels in its display config, saved views included, and where the host has no right panel the task opens in the main container ([client/task-opening.ts](client/task-opening.ts)). Inside that tab and inside the thread's task panel a sub-task or the parent opens in the same panel, and a back button left of the key returns to the task before it; the panel keeps that trail while it is mounted and starts it over on every open from outside ([shared/task-trail.ts](shared/task-trail.ts)).
- `app.slots.threadPanelAction` (id `task`) — a **Task** tab in a thread's right panel (`TaskEmbedPanel`).
- `app.slots.experimental_threadHeaderAction` (id `current-task`) — a task action in the thread header (`CurrentTaskHeaderAction`).
- `app.slots.messageDirective` (id `task`) — renders the `::task{key="…"}` leaf directive inline in a message as a task card (`TaskDirectiveCard`).

The backend ([server.ts](server.ts)) wires the store and its feature modules: `registerTasksApi` (RPC — the only bridge the frontend uses), `registerAttachments`, `registerTasksCli` (the `bb tasks` CLI), `registerDelegation`, `registerMentions`, `registerFolders`, and `registerLifecycle`. Mentions register through `bb.ui.registerMentionProvider` (id `task`, label **Tasks**) so typing `@` in the composer searches tasks by key or title and hands the agent the task's context.

Data comes from disk, not SQL. `createStore` loads a file-backed store where each task is a Markdown file in a status folder (see [decisions/tasks-files-are-the-store.md](decisions/tasks-files-are-the-store.md) and [decisions/tasks-every-file-in-a-status-folder-is-a-task.md](decisions/tasks-every-file-in-a-status-folder-is-a-task.md)); every call looks at the files afresh, but a file is parsed again only when its stat changed ([filesync/parse-cache.ts](filesync/parse-cache.ts)) and calls that arrive together, with no write of the store between them, share one read of the board — so views ask for whole boards at once rather than per task: the board and the table draw from `listTasks` and fetch every card's attachment count and threads with one `taskCardMeta` call — while boards, folders, presets, saved views, each project's manual order of tasks and the tokens of database boards live in `bb.storage.kv` — not in bb's secret settings, which bb erases whenever the plugin is removed or reinstalled ([folders/database-secrets.ts](folders/database-secrets.ts)). `listTasks` gives a project's tasks in that manual order — tasks nobody placed yet first, newest on top; the list of every project instead carries todo, in_progress and in_review first, then backlog, then done and canceled, and a page hands out `nextCursor` until the list ends ([filesync/task-page.ts](filesync/task-page.ts)) — and `boardMove` rewrites it from the neighbours of a drop ([shared/manual-order.ts](shared/manual-order.ts), [filesync/order-store.ts](filesync/order-store.ts), [docs/decisions/tasks-plus-manual-order-in-plugin-kv.md](../docs/decisions/tasks-plus-manual-order-in-plugin-kv.md)). The workflow fields are serialized into each file's YAML frontmatter — `type`, `estimate`, `minutes` (Planned Time), `minutes_actual` (Actual Time), `budget`, `limit`, `cost`, `due` (Due date) and `start` (Start date) — by [filesync/task-file.ts](filesync/task-file.ts). Legacy `tokens`, `tokens_actual` and `checks` lines are neither read nor removed; a saved view that still lists the retired `tokens` field is served without it. The `flow` block (`id`, `name`) is written by the Flow plugin, not by the board: a run's stage that hands the task file back as a result stamps the thread's flow into it, the board reads it into `Task.flow` and never writes it, and the task card shows it as a link to the flow's page in Flow ([shared/flow-route.ts](shared/flow-route.ts)).

A table and a board share one header ([views/board/toolbar.tsx](views/board/toolbar.tsx)): the view's name, the active filters and the sort as chips, Save view — or Reset and Save on an open saved view — once the view moved off what it saved, then Sort, Filter and Display. A field picked from Filter shows its chip with the values menu open beneath it; the chip stays, empty too, until its cross or another screen or view, a click on it opening and closing the menu, and an empty chip is never saved. Menus, popovers, selects and dialogs hang in an element of the panel's own — of the Tasks+ page, of the Task tab beside it and of the thread's task panel — not on the page's body: bb drops a node React made into a parent React does not own while any plugin's async work is in flight, and an overlay portaled to the body then never shows ([components/ui/overlay-container.tsx](components/ui/overlay-container.tsx)); the phone's drawers still open on the body. A table row off the screen is left out of the browser's styling and layout (`content-visibility: auto`), so a change anywhere on a long table no longer restyles every row. Sort offers every field Filter does and Open sub-tasks — the open tasks at any depth under a task, open being what analytics counts open ([shared/enums.ts](shared/enums.ts)) — and marks the sorted field with an arrow the way it runs. Which table or board a route shows is decided once, for the header and the panel alike ([shell/view-target.ts](shell/view-target.ts)). Display opens a panel beside the tasks, over them on a narrow screen, with everything that is not a filter or a sort: Table or Board — on every screen of tasks and on every saved view, remembered per screen and per view ([shell/view-preference.ts](shell/view-preference.ts)) — the grouping of the table's rows and of the board's columns, the fields in their order, the sub-task list, the card charts, empty values, Open in side panel ([views/common/display-panel.tsx](views/common/display-panel.tsx)). The table's filters live in a store the header writes and the table reads ([views/common/list-preference.ts](views/common/list-preference.ts)); its column sort, grouping, widths, pinned columns and folded groups live per screen beside them ([views/table/table-preference.ts](views/table/table-preference.ts)). The table itself is columns of the fields: a click on a header opens its menu — sort ascending or descending, pin, hide, and on a column of dates its format (date and time, date, relative) and on a column with a decorative icon Show icon ([views/table/column-display.ts](views/table/column-display.ts)) — a header is dragged to move its column — a line marks where it lands, and the drag never opens the menu — and its edge to resize it, pinned columns lead and stay put when the table scrolls sideways, as do the group names and New task rows, sub-tasks sit under their parent and fold with it, and rows group by the same properties as the board ([views/table/columns.ts](views/table/columns.ts), [views/table/rows.ts](views/table/rows.ts), [views/table/index.tsx](views/table/index.tsx)). The Parent filter keeps the tasks lying under the picked ones at any depth; its chip opens a field to type in over the tasks that have tasks under them, epics first, narrowed by key, slug and title ([views/common/lib.ts](views/common/lib.ts), `idsUnder` in [shared/subtree.ts](shared/subtree.ts)). It took the place of the epic filter: a view saved with one keeps everything but that filter ([filesync/saved-view-migrate.ts](filesync/saved-view-migrate.ts)).

The board is laid out by a layout of its own — filters, sort and grouping — kept per board in the browser like the table's preferences ([views/board/board-preference.ts](views/board/board-preference.ts)); a board belongs to its screen — a project, All tasks, Active or Waiting — or to a saved view opened on it, so opening a view never rewrites the screen's board; a cross-project board reads every project on the screen and keeps no hand-set order inside a column ([views/board/scope-data.ts](views/board/scope-data.ts)). The pure core [views/board/grouping.ts](views/board/grouping.ts) turns tasks and a layout into columns — by status, priority, type, estimate, assignee, label, or one grid when ungrouped, as many columns wide as the Display panel sets (Auto fits 15rem cards, or a fixed one to six); on a grouped board Fill width fits the columns to the board's width, each growing by an equal share of the spare room or shrinking by its width's share of the shortfall — and tells what a drop into another column changes: status goes through `boardMove`, any other property goes through `updateTask`. Under the Manual sort a card is also dragged to another place inside its status column or across the ungrouped grid, and `boardMove` keeps that place in the project's manual order. On a phone — a narrow screen under a finger — a card is dragged only by the grip strip along its right edge, marked with three lines, and a finger on the rest of the card scrolls the column and taps it open. Every task is a card, a child too, marked with its parent. Besides the table's fields the board's Display panel offers Sub-task list (everything under the card, each row opening its task, with Add sub-task under the rows — on a card with none too — typing a title into the card and Enter making it a sub-task in To do, [views/board/subtask-list.tsx](views/board/subtask-list.tsx); the Display panel narrows it to the open sub-tasks at any depth, a closed one kept only as the parent of an open one, or to the open children one level down — open being neither done nor canceled), Sub-task stats (the spread over statuses and the share done), Burndown (the open tasks under the card over the board's period, the trend dashed, served by one `taskBurndowns` call per board from the transition log, [analytics/burndown.ts](analytics/burndown.ts)) and Sub-task Gantt (a lane per task under the card: the planned dates outlined, the working statuses it actually stood in — In progress and In review — filled from the transition log, Backlog and To do left out, or both laid over each other, served by one `ganttRows` call per board, [analytics/gantt.ts](analytics/gantt.ts), drawn by [views/analytics/gantt-chart.tsx](views/analytics/gantt-chart.tsx)). The period — a number of days, hours or minutes typed in, 0 for all time by the week — where today stands in it — Right looks back over the past, Center watches the present, half back and half ahead, Left plans ahead, the Gantt drawing the plans and the burndown its dashed trend past a line at today; both charts of a card draw one window by time, so today stands at the same spot in each, in the exact middle when centered ([views/board/chart-window.ts](views/board/chart-window.ts)) — the dates — off, under each chart or once along the card's bottom, few, some or many of them, at round minutes, hours, midnights, Mondays or firsts of a month ([views/board/date-ticks.ts](views/board/date-ticks.ts)) — and what the Gantt shows are picked once per board in the Display panel and kept in the browser apart from the layout ([views/board/chart-preference.ts](views/board/chart-preference.ts)); so are the type sizes of the card's title, description and sub-task list, under Card text ([views/board/card-text-preference.ts](views/board/card-text-preference.ts)); Status, Slug and Sub-tasks — done out of everything under the task — are on both surfaces ([shared/subtree.ts](shared/subtree.ts)). The task key is a field too, Key, shown by default: on the card it stands in a row of chips among the other fields, in the table row it keeps its column left of the title; switching it off takes it away. Description, dragged like any other field, puts the first paragraph of the description on the card (a board that had Show description on before it was a field keeps it on) — headings, code and markup passed over ([shared/first-paragraph.ts](shared/first-paragraph.ts)). The card draws nothing but the fields, in the Display panel's order: Title is a field too — moved like the others, never hidden — and so are what the card once pinned above it, Parent, Slug, Active (the working agents), Worktree (a task read from a thread's worktree), and the Attachments clip. Chips that follow each other share a row, and each full-width field — Title, Description, Sub-task list, Sub-task stats, Burndown, Sub-task Gantt — stands where the panel lists it, splitting the chips around it into a row above and a row below; with every field off the card is its title alone ([views/board/card-sections.ts](views/board/card-sections.ts)). A board set up before Title was a field keeps its look: its old top line — slug as it was, agents, parent, worktree — goes above the title, the clip to the end ([views/common/row-field-preference.ts](views/common/row-field-preference.ts)). A Gantt row names its task on hover — key and title, status, plan Start → Due — and a click on that tooltip opens it; a task's line ends where it was done, marked with the Done icon — a task done without a stretch of work gets the mark alone. A tag on the card and in the rail is filled with its own colour, the text black or white by its lightness ([views/common/label-fill.ts](views/common/label-fill.ts)). How narrow and how wide a column may be dragged, and how wide it starts, are three numbers in the plugin's settings under Board columns — 200, 480 and 230 px until changed, whole pixels between 80 and 2000 with the minimum, the default and the maximum in that order ([shared/board-column-width.ts](shared/board-column-width.ts), [shell/board-column-width-setting.tsx](shell/board-column-width-setting.tsx)); a width dragged or saved before they changed is held inside them when it is read, so a saved view never stops opening, and Fill width still has no upper edge. A saved view names its `surface`, `table` or `board`; a board view carries its grouping in `board`, and an open one offers Reset and Save once its layout moves off what it saved.

A record's own properties are the frontmatter keys with a single value — text, a number, yes or no — that the board does not read itself ([shared/properties.ts](shared/properties.ts)). The card shows them above the description as a Properties grid, where a property is added, renamed, edited and removed in place ([views/detail/properties.tsx](views/detail/properties.tsx)); the table draws a column for every property name its records have, after the regular columns, hidden from the column's header and brought back from Properties, per board in the browser ([views/table/property-columns.ts](views/table/property-columns.ts)). Values are text: no types, filters or grouping yet. The grid and the mirror folder row are Shapeshift components copied into [components/shapeshift](components/shapeshift) ([decision](../docs/decisions/tasks-plus-shapeshift-vendored.md)).

A database board can be mirrored into a folder of this machine: Mirror folder in its row of Manage → Projects, a full path or one from `~/`. Every poll that brings a change writes each live record into the folder as a file of the same text, named by its key — by its slug while it has none — and takes a deleted record's file away ([filesync/folder-mirror.ts](filesync/folder-mirror.ts)). The mirror lists the files it wrote in `.tasks-mirror.json` and touches no other file. It is one way only: a file edited by hand never reaches the database, and the next change of its record writes over it — edit records in the card or with `bb tasks update`.

A project kept in a database can hold sections beside its task board, and a section can hold sections of its own, as deep as needed: the "+" at the end of a project's or a section's row in the left column — standing where the record count was — names a new one, the name field keeps a loader until the section is on the list, and the section stands under its parent there, a step further in. Each section keeps its records in its own pair of tables of the same database and is listed, with the section it sits in, in the database's `tables`, so every machine on the database shows it on its next poll; the task board keeps its own `tasks` and `board` tables and reads the same for a plugin of an older version ([filesync/db-tables.ts](filesync/db-tables.ts)). A section's record has no task fields. A section's field has a name and a type — Text, Number, Select, Tags, Date, Checkbox or URL; a Select holds one of its options and Tags several, picked from a list where a typed name becomes a new option and a bin takes one away; every section starts with Tags and Date, the Tags being the record's labels — picked like a task's labels, drawn as their chips in the colours Manage → Labels gave them and written as `tags:` in Kasimov — the fields added after them are listed with their types in the database's `tables`, so a colleague sees the same ones, and a frontmatter key a record has beyond them is a Text field ([shared/section-fields.ts](shared/section-fields.ts)). The section's table is the task table over its own columns — the title, the record's text (Description, hidden until Display shows it), Created, Edited and a column per field — each with the same header menu, width and drag; the "+" at the end of the header adds a field by name and type, and a hidden column comes back from Display ([views/table/section-table.tsx](views/table/section-table.tsx)). New record makes an Untitled record and opens it, in Kasimov — the document view of MD Opener — or in the task card, as the switch above the record says; the card stands on the page with no frame around it, and its Properties are the table's columns, each edited the way its type reads; like any task card, it shows a change at once and saves it in the background, putting the field back with the reason when the write is refused ([views/detail/pending-update.ts](views/detail/pending-update.ts), [views/detail/section-properties.tsx](views/detail/section-properties.tsx)). Kasimov shows the title, every field of the section and the two dates as frontmatter; its Save writes the title, the fields and the text back to the database, never the dates, and refuses an edit made over someone else's ([filesync/section-text.ts](filesync/section-text.ts), [views/detail/record-doc.tsx](views/detail/record-doc.tsx)). A mirrored project mirrors each section into a folder inside its parent's. In the left column a project's sections fold away by the chevron that replaces its icon on hover, by the arrows, or all at once by the 1 · 2 · 3 switch over Projects — the folding is Shapeshift's tree ([shell/section-tree.ts](shell/section-tree.ts)); a section, never a project, is renamed or deleted — with its records and the sections inside it, for everyone on the database — from its "⋯" menu.

Delegated agent threads are tracked live through bb lifecycle events (`thread.created/active/idle/failed/archived/deleted`) plus a `thread-status-reconcile` background service that recovers transitions missed while the plugin was unloaded ([lifecycle/index.ts](lifecycle/index.ts)); thread live-state is process memory and is deliberately not written back into the task file (see [decisions/tasks-plus-thread-state-is-not-a-file-field.md](decisions/tasks-plus-thread-state-is-not-a-file-field.md)). An agent that started a workflow or background agents ends its turn and waits for them, so bb reports the thread idle while the work goes on; bb shows that work only to the frontend, through the sidebar's live view, so an invisible app overlay ([shell/busy-threads-reporter.tsx](shell/busy-threads-reporter.tsx)) hands the set of such threads to the `reportBusyThreads` RPC, and the store reads them as working — in Active, out of Waiting, with the live-agent chip on — without touching the turn's own state (`withBackgroundWork` in [threads/live-state.ts](threads/live-state.ts)). A background command does not count: a dev server outlives the turn. The `--active` flag of the CLI has no sidebar and still reads the turn alone.

# Tasks+ — по-русски

> Форк плагина Tasks: задачи хранятся Markdown-файлами на диске, добавлены нативные поля рабочего процесса — Type, Estimate, Check, время и бюджет.

## Для чего нужен

Tasks+ — трекер в стиле Linear внутри bb (id плагина `tasks-plus`) для планирования работы, делегирования её агентам и связи записи о задаче с тредами, которые её делают. Он переносит всё, что даёт встроенный плагин Tasks — проекты и папки, ключи задач, статусы и приоритеты, метки, подзадачи, Markdown-комментарии, вложения, пресеты агентов и делегирование, упоминания задач и полный CLI `bb tasks`, — и забирает себе имя этого CLI, чтобы заменить встроенный плагин.

Поверх этой базы он добавляет нативные поля для workflow проектной памяти, редактируемые в рейле задачи: **Type** (epic, feature, bugfix, spike, refactor, migration, design), **Estimate** (xs, s, m, l, xl), **Check** (мультивыбор из test, review, design, browser), **Planned Time** и **Actual Time** в целых минутах, **Budget**, **Limit** и **Cost** в долларах с точностью до цента, **Start date** и **Due date** — запланированные начало и окончание работ. Type, Estimate, время, деньги и обе даты допускают пустое значение — задачу можно оставить без них, как `priority = none`.

Эпик — обычная задача типа Epic. Подзадачи вкладываются на любую глубину, а задача входит в эпик, который ближе всех к ней среди предков типа Epic, что бы ни лежало между ними; тип задачи ничего не делает с её детьми. Этого предка доска вычисляет при чтении задач ([shared/epic.ts](shared/epic.ts), `Task.epicId`); его называет `bb tasks show`, а на доске поля Epic нет — место задачи под эпиком читается через Parent; а в эпик задачу кладут, делая эпик её родителем (меню Parent в рейле, `bb tasks update --epic <ключ>`). Старые папки эпиков `<исполнитель>/<эпик>/<статус>/` читаются, пока `bb tasks epics migrate` не превратит каждую в задачу-эпик и не перенесёт её файлы к ней ([filesync/epic-migrate.ts](filesync/epic-migrate.ts)). На доске каждая задача — карточка, дочерняя с отметкой родителя; в меню полей карточки есть Sub-task list — под строками стоит Add sub-task, и у карточки без подзадач тоже: название вводится прямо в карточке, Enter заводит подзадачу в To do; в нём же выбор: все подзадачи, все открытые (закрытая остаётся только родителем открытой) или открытые первого уровня, открытая — не Done и не Canceled, — Sub-task stats, Burndown — открытые потомки за период доски по журналу переходов ([analytics/burndown.ts](analytics/burndown.ts)), и Sub-task Gantt — полоса на каждого потомка: плановые даты контуром, фактические рабочие статусы из журнала — In progress и In review — заливкой, Backlog и To do не рисуются, Done — отметкой или оба сразу ([analytics/gantt.ts](analytics/gantt.ts), [views/analytics/gantt-chart.tsx](views/analytics/gantt-chart.tsx)); период — число дней, часов или минут, 0 — всё время по неделям, — положение «сегодня» в нём — Right смотрит в прошлое, Center следит за текущим, Left планирует вперёд, Гант рисует планы, а Burndown — пунктир тренда за линией «сегодня»; оба графика карточки рисуют одно окно по времени, и «сегодня» стоит у них в одной точке, по центру — ровно посередине ([views/board/chart-window.ts](views/board/chart-window.ts)), — даты — выключены, под каждым графиком или один раз внизу карточки, редко, средне или часто, на круглых минутах, часах, полуночах, понедельниках или первых числах ([views/board/date-ticks.ts](views/board/date-ticks.ts)), — и режим Ганта выбираются один раз на доску в панели Display и хранятся в браузере отдельно от раскладки ([views/board/chart-preference.ts](views/board/chart-preference.ts)), а Status, Slug и Sub-tasks — и в таблице, и на доске. Ключ задачи — тоже поле, Key, включённое по умолчанию: на карточке оно в ряду чипов среди остальных полей, в строке таблицы — в своей колонке слева от заголовка; выключенное пропадает. Description — первое по умолчанию поле списка полей доски, перетаскивается как остальные — выводит на карточке первый абзац описания — без заголовков, кода и разметки ([shared/first-paragraph.ts](shared/first-paragraph.ts)). Под заголовком карточка рисует поля в порядке меню Display: идущие подряд чипы делят один ряд, а каждое поле во всю ширину — Description, Sub-task list, Sub-task stats, Burndown, Sub-task Gantt — встаёт там, где оно стоит в меню, и делит чипы вокруг себя на ряд выше и ряд ниже; скрепка вложений замыкает последний ряд чипов, а у карточки без чипов стоит одна внизу ([views/board/card-sections.ts](views/board/card-sections.ts)). Fill width в разделе Columns подгоняет колонки доски под её ширину: каждая растягивается на равную долю свободного места или сжимается пропорционально своей ширине. Доска без группировки — одна сетка, число её колонок задаёт меню Group: Auto укладывает сколько влезет карточек по 15rem, либо ровно от одной до шести. При сортировке Manual карточку перетаскивают на другое место и внутри колонки статуса, и по сетке без группировки, а `boardMove` запоминает это место в ручном порядке проекта. На телефоне — узкий экран и палец — карточку тащат только за полосу у её правого края с иконкой из трёх полосок, а палец на остальной карточке прокручивает колонку и тапом открывает задачу.

Второе принципиальное отличие от оригинала — где живут задачи: задача это Markdown-файл в папке статуса на диске, а не строка в базе. Метаданные доски (папки, пресеты, сохранённые виды) по-прежнему хранятся в хранилище плагина, но сами задачи читаются заново из своих файлов, а каждая правка из панели коммитится и пушится в git-репозиторий доски.

## Как устроено

Фронтенд занимает четыре слота хоста в [app.tsx](app.tsx):

- `app.slots.navPanel` — основная панель **Tasks+** по пути `tasks`, её рисует `TasksAppShell`, с `experimental_sidebarAccessory` (`TasksSidebarAccessory`) в подвале сайдбара. Навигация — колонка этой панели рядом с областью, которой она правит; на узком экране помещается одна, поэтому панель открывается на области, а кнопка топбара приводит навигацию во всю ширину ([shell/columns.ts](shell/columns.ts)).
- `app.slots.threadPanelAction` (id `task`) — вкладка **Task** в правой панели треда (`TaskEmbedPanel`).
- `app.slots.experimental_threadHeaderAction` (id `current-task`) — действие задачи в шапке треда (`CurrentTaskHeaderAction`).
- `app.slots.messageDirective` (id `task`) — рендерит листовую директиву `::task{key="…"}` в сообщении карточкой задачи (`TaskDirectiveCard`).

Бэкенд ([server.ts](server.ts)) собирает store и его модули: `registerTasksApi` (RPC — единственный мост, которым пользуется фронтенд), `registerAttachments`, `registerTasksCli` (CLI `bb tasks`), `registerDelegation`, `registerMentions`, `registerFolders` и `registerLifecycle`. Упоминания регистрируются через `bb.ui.registerMentionProvider` (id `task`, метка **Tasks**): `@` в композере ищет задачи по ключу или заголовку и отдаёт агенту контекст задачи.

Данные берутся с диска, а не из SQL. `createStore` поднимает файловый store, где каждая задача — Markdown-файл в папке статуса (см. [decisions/tasks-files-are-the-store.md](decisions/tasks-files-are-the-store.md) и [decisions/tasks-every-file-in-a-status-folder-is-a-task.md](decisions/tasks-every-file-in-a-status-folder-is-a-task.md)); каждый вызов смотрит на файлы заново, но файл разбирается повторно, только когда изменился его stat ([filesync/parse-cache.ts](filesync/parse-cache.ts)), а вызовы, пришедшие вместе без записи между ними, делят одно чтение доски — поэтому экраны просят доску целиком, а не по задаче: доска и таблица рисуются из `listTasks`, а число вложений и треды всех карточек берут одним вызовом `taskCardMeta`, — а доски, папки, пресеты, сохранённые виды, ручной порядок задач каждого проекта и токены досок на базе лежат в `bb.storage.kv` — не в секретных настройках bb, которые bb стирает при каждом снятии или переустановке плагина ([folders/database-secrets.ts](folders/database-secrets.ts)). `listTasks` отдаёт задачи проекта в этом ручном порядке — ещё не расставленные первыми, новые сверху; а список всех проектов несёт сперва todo, in_progress и in_review, потом backlog, потом done и canceled, и страница выдаёт `nextCursor`, пока список не кончится ([filesync/task-page.ts](filesync/task-page.ts)), — а `boardMove` переписывает его по соседям сброса карточки ([shared/manual-order.ts](shared/manual-order.ts), [filesync/order-store.ts](filesync/order-store.ts), [docs/decisions/tasks-plus-manual-order-in-plugin-kv.md](../docs/decisions/tasks-plus-manual-order-in-plugin-kv.md)). Поля workflow сериализуются в YAML-frontmatter каждого файла — `type`, `estimate`, `minutes` (Planned Time), `minutes_actual` (Actual Time), `budget`, `limit` и `cost` — модулем [filesync/task-file.ts](filesync/task-file.ts). Старые строки `tokens`, `tokens_actual` и `checks` плагин не читает и не стирает; сохранённый вид, где ещё значится снятое поле `tokens`, отдаётся без него. Блок `flow` (`id`, `name`) пишет не доска, а плагин Flow: этап прогона, отдавший файл задачи результатом, ставит в него flow треда; доска читает блок в `Task.flow`, сама его не пишет, а карточка задачи показывает его ссылкой на страницу flow во Flow ([shared/flow-route.ts](shared/flow-route.ts)).

Свои свойства записи — ключи frontmatter с одним значением (текст, число, да или нет), которых доска сама не читает ([shared/properties.ts](shared/properties.ts)). Карточка показывает их над описанием сеткой Properties: свойство добавляется, переименовывается, правится и удаляется на месте ([views/detail/properties.tsx](views/detail/properties.tsx)); таблица рисует колонку на каждое имя свойства своих записей после обычных колонок, колонка скрывается из своего заголовка и возвращается из меню Properties, по доске в браузере ([views/table/property-columns.ts](views/table/property-columns.ts)). Значения — текст: типов, фильтров и группировки пока нет. Сетка и строка папки зеркала — компоненты Shapeshift, скопированные в [components/shapeshift](components/shapeshift) ([решение](../docs/decisions/tasks-plus-shapeshift-vendored.md)).

Доску на базе можно зеркалить в папку этой машины: Mirror folder в её строке в Manage → Projects, полный путь или путь от `~/`. Каждый опрос, принёсший изменение, пишет живые записи в папку файлами с тем же текстом, по ключу записи — без ключа по slug, — а файл удалённой записи убирает ([filesync/folder-mirror.ts](filesync/folder-mirror.ts)). Свои файлы зеркало помнит в `.tasks-mirror.json` и чужих не трогает. Зеркало одностороннее: правка файла руками в базу не попадает и перезаписывается следующим изменением записи — записи правятся в карточке или командой `bb tasks update`.

В проекте на базе можно завести разделы рядом с доской задач, а в разделе — свои разделы, на любую глубину: «+» в конце строки проекта или раздела в левой колонке — на месте числа записей — спрашивает имя нового, поле имени держит лоадер, пока раздел не появится в списке, и раздел встаёт там под своим родителем, на шаг правее. Записи каждого раздела лежат в своей паре таблиц той же базы, а сам он вместе с родителем — в списке `tables` базы, поэтому любая машина на этой базе показывает его со следующего опроса; доска задач остаётся на своих `tasks` и `board` и читается плагином прежней версии как раньше ([filesync/db-tables.ts](filesync/db-tables.ts)). У записи раздела нет полей задачи. У поля раздела есть имя и тип — Text, Number, Select, Tags, Date, Checkbox или URL; Select хранит один вариант, Tags — несколько, их выбирают из списка, где набранное имя становится новым вариантом, а корзина убирает вариант; каждый раздел начинает с Tags и Date, и эти Tags — лейблы записи: выбираются как лейблы задачи, видны их чипами и пишутся в Касимове строкой `tags:`; поля, добавленные после них, записаны с типами в списке `tables` базы, поэтому коллега видит те же, а ключ frontmatter записи сверх них — поле Text ([shared/section-fields.ts](shared/section-fields.ts)). Таблица раздела — та же таблица задач над его колонками: название, текст записи (Description, скрыт, пока его не покажет Display), Created, Edited и колонка на поле, у каждой то же меню заголовка, ширина и перетаскивание; «+» в конце заголовка добавляет поле по имени и типу, а скрытая колонка возвращается из Display ([views/table/section-table.tsx](views/table/section-table.tsx)). New record заводит запись Untitled и открывает её Касимовым — видом документа MD Opener — или карточкой задачи, как скажет переключатель над записью; карточка стоит на странице без рамки, а свойства в ней — колонки таблицы, каждая правится по своему типу ([views/detail/section-properties.tsx](views/detail/section-properties.tsx)). Касимов показывает название, все поля раздела и две даты frontmatter'ом; его Save пишет название, поля и текст обратно в базу, но не даты, и не пишет поверх чужой правки ([filesync/section-text.ts](filesync/section-text.ts), [views/detail/record-doc.tsx](views/detail/record-doc.tsx)). Зеркало проекта кладёт каждый раздел в папку внутри папки его родителя. В левой колонке разделы проекта сворачиваются шевроном, который встаёт на место иконки при наведении, стрелками или все сразу переключателем 1 · 2 · 3 над Projects — сворачивание взято из дерева Shapeshift ([shell/section-tree.ts](shell/section-tree.ts)); раздел, но не проект, переименовывается и удаляется — вместе с записями и вложенными разделами, у всех на базе — из его меню «⋯».

Делегированные треды агентов отслеживаются вживую через события жизненного цикла bb (`thread.created/active/idle/failed/archived/deleted`) плюс фоновый сервис `thread-status-reconcile`, который восстанавливает переходы, пропущенные пока плагин был выгружен ([lifecycle/index.ts](lifecycle/index.ts)); живое состояние треда держится в памяти процесса и намеренно не пишется обратно в файл задачи (см. [decisions/tasks-plus-thread-state-is-not-a-file-field.md](decisions/tasks-plus-thread-state-is-not-a-file-field.md)). Агент, запустивший workflow или фоновых агентов, заканчивает ход и ждёт их, и bb сообщает о треде как о стоящем, хотя работа идёт; эту работу bb показывает только фронтенду, через живой список сайдбара, поэтому невидимый оверлей ([shell/busy-threads-reporter.tsx](shell/busy-threads-reporter.tsx)) отдаёт набор таких тредов в RPC `reportBusyThreads`, и хранилище читает их работающими — в Active, не в Waiting, со значком живого агента — не трогая собственное состояние хода (`withBackgroundWork` в [threads/live-state.ts](threads/live-state.ts)). Фоновая команда не в счёт: dev-сервер переживает ход. Флаг `--active` команды CLI сайдбара не видит и по-прежнему читает только ход.
