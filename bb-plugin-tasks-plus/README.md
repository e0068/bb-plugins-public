# Tasks+

> A fork of the Tasks plugin that keeps tasks as Markdown files on disk and adds native workflow fields — Type, Estimate, Check, time and budget.

## What it does

Tasks+ is a Linear-style tracker inside bb (plugin id `tasks-plus`) for planning work, delegating it to agents, and keeping the task record connected to the threads doing the work. It carries over everything the built-in Tasks plugin offers — projects and folders, task keys, statuses and priorities, labels, subtasks, Markdown comments, attachments, agent presets and delegation, task mentions, and the full `bb tasks` CLI — and takes over that CLI name so it can replace the built-in plugin.

On top of that base it adds native fields for the project-memory workflow, editable in a task's detail rail: **Type** (epic, feature, bugfix, spike, refactor, migration, design), **Estimate** (xs, s, m, l, xl), **Check** (a multi-select of test, review, design, browser), **Planned Time** and **Actual Time** in whole minutes, and **Budget**, **Limit** and **Cost** in dollars to the cent. Type, Estimate, time and money are nullable — a task can be left unset, like `priority = none`.

An epic is an ordinary task typed epic. Sub-tasks nest to any depth, and a task belongs to the epic that is its nearest ancestor typed epic — whatever lies between, and a task's own type does nothing to its children. The board works that ancestor out when it reads the tasks ([shared/epic.ts](shared/epic.ts), `Task.epicId`); `bb tasks show` names it — the board has no Epic field, a task's place under an epic reads through Parent — and a task goes into an epic by taking the epic as its parent (the rail's Parent menu, `bb tasks update --epic <key>`). The older epic folders `<assignee>/<epic>/<status>/` are still read until `bb tasks epics migrate` turns each into an epic task and moves its files up beside it ([filesync/epic-migrate.ts](filesync/epic-migrate.ts)).

The other defining difference from the original is where tasks live: a task is a Markdown file in a status folder on disk, not a row in a database. Board metadata (folders, presets, saved views) is still kept in plugin storage, but the tasks themselves are read fresh from their files, and every edit made from the panel is committed and pushed to the board's git repository.

## How it works

The frontend registers four host slots in [app.tsx](app.tsx):

- `app.slots.navPanel` — the main **Tasks+** panel at path `tasks`, rendered by `TasksAppShell`, with an `experimental_sidebarAccessory` (`TasksSidebarAccessory`) for the sidebar footer. Navigation is a column of that panel, beside the area it navigates; on a narrow screen there is room for one, so the panel opens on the area and the topbar button brings navigation over the full width ([shell/columns.ts](shell/columns.ts)). Its `fixedTabs` add a **Task** tab to the page's right panel (`TaskSidePanelTab`): with Open in side panel on in a board's or table's Display panel, its cards or rows open there and the board or table stays in place; the choice belongs to that board or table and travels in its display config, saved views included, and where the host has no right panel the task opens in the main container ([client/task-opening.ts](client/task-opening.ts)). Inside that tab and inside the thread's task panel a sub-task or the parent opens in the same panel, and a back button left of the key returns to the task before it; the panel keeps that trail while it is mounted and starts it over on every open from outside ([shared/task-trail.ts](shared/task-trail.ts)).
- `app.slots.threadPanelAction` (id `task`) — a **Task** tab in a thread's right panel (`TaskEmbedPanel`).
- `app.slots.experimental_threadHeaderAction` (id `current-task`) — a task action in the thread header (`CurrentTaskHeaderAction`).
- `app.slots.messageDirective` (id `task`) — renders the `::task{key="…"}` leaf directive inline in a message as a task card (`TaskDirectiveCard`).

The backend ([server.ts](server.ts)) wires the store and its feature modules: `registerTasksApi` (RPC — the only bridge the frontend uses), `registerAttachments`, `registerTasksCli` (the `bb tasks` CLI), `registerDelegation`, `registerMentions`, `registerFolders`, and `registerLifecycle`. Mentions register through `bb.ui.registerMentionProvider` (id `task`, label **Tasks**) so typing `@` in the composer searches tasks by key or title and hands the agent the task's context.

Data comes from disk, not SQL. `createStore` loads a file-backed store where each task is a Markdown file in a status folder (see [decisions/tasks-files-are-the-store.md](decisions/tasks-files-are-the-store.md) and [decisions/tasks-every-file-in-a-status-folder-is-a-task.md](decisions/tasks-every-file-in-a-status-folder-is-a-task.md)); every call looks at the files afresh, but a file is parsed again only when its stat changed ([filesync/parse-cache.ts](filesync/parse-cache.ts)) and calls that arrive together, with no write of the store between them, share one read of the board — so views ask for whole boards at once rather than per task: the board and the table draw from `listTasks` and fetch every card's attachment count and threads with one `taskCardMeta` call — while boards, folders, presets, saved views and each project's manual order of tasks live in `bb.storage.kv`. `listTasks` gives a project's tasks in that manual order — tasks nobody placed yet first, newest on top — and `boardMove` rewrites it from the neighbours of a drop ([shared/manual-order.ts](shared/manual-order.ts), [filesync/order-store.ts](filesync/order-store.ts), [docs/decisions/tasks-plus-manual-order-in-plugin-kv.md](../docs/decisions/tasks-plus-manual-order-in-plugin-kv.md)). The workflow fields are serialized into each file's YAML frontmatter — `type`, `estimate`, `minutes` (Planned Time), `minutes_actual` (Actual Time), `budget`, `limit`, `cost`, `due` (Due date) and `start` (Start date) — by [filesync/task-file.ts](filesync/task-file.ts). Legacy `tokens`, `tokens_actual` and `checks` lines are neither read nor removed; a saved view that still lists the retired `tokens` field is served without it. The `flow` block (`id`, `name`) is written by the Flow plugin, not by the board: a run's stage that hands the task file back as a result stamps the thread's flow into it, the board reads it into `Task.flow` and never writes it, and the task card shows it as a link to the flow's page in Flow ([shared/flow-route.ts](shared/flow-route.ts)).

A table and a board share one header ([views/board/toolbar.tsx](views/board/toolbar.tsx)): the view's name, the active filters and the sort as chips, Save view — or Reset and Save on an open saved view — once the view moved off what it saved, then Sort, Filter and Display. Which table or board a route shows is decided once, for the header and the panel alike ([shell/view-target.ts](shell/view-target.ts)). Display opens a panel beside the tasks, over them on a narrow screen, with everything that is not a filter or a sort: Table or Board — on every screen of tasks and on every saved view, remembered per screen and per view ([shell/view-preference.ts](shell/view-preference.ts)) — the grouping of the table's rows and of the board's columns, the fields in their order, the sub-task list, the card charts, empty values, Open in side panel ([views/common/display-panel.tsx](views/common/display-panel.tsx)). The table's filters live in a store the header writes and the table reads ([views/common/list-preference.ts](views/common/list-preference.ts)); its column sort, grouping, widths, pinned columns and folded groups live per screen beside them ([views/table/table-preference.ts](views/table/table-preference.ts)). The table itself is columns of the fields: a click on a header opens its menu — sort ascending or descending, pin, hide — a header is dragged to move its column — a line marks where it lands, and the drag never opens the menu — and its edge to resize it, pinned columns lead and stay put when the table scrolls sideways, as do the group names and New task rows, sub-tasks sit under their parent and fold with it, and rows group by the same properties as the board ([views/table/columns.ts](views/table/columns.ts), [views/table/rows.ts](views/table/rows.ts), [views/table/index.tsx](views/table/index.tsx)). The Parent filter keeps the tasks lying under the picked ones at any depth; its chip opens a field to type in over the tasks that have tasks under them, epics first, narrowed by key, slug and title ([views/common/lib.ts](views/common/lib.ts), `idsUnder` in [shared/subtree.ts](shared/subtree.ts)). It took the place of the epic filter: a view saved with one keeps everything but that filter ([filesync/saved-view-migrate.ts](filesync/saved-view-migrate.ts)).

The board is laid out by a layout of its own — filters, sort and grouping — kept per board in the browser like the table's preferences ([views/board/board-preference.ts](views/board/board-preference.ts)); a board belongs to its screen — a project, All tasks, Active or Waiting — or to a saved view opened on it, so opening a view never rewrites the screen's board; a cross-project board reads every project on the screen and keeps no hand-set order inside a column ([views/board/scope-data.ts](views/board/scope-data.ts)). The pure core [views/board/grouping.ts](views/board/grouping.ts) turns tasks and a layout into columns — by status, priority, type, estimate, assignee, label, or one grid when ungrouped, as many columns wide as the Display panel sets (Auto fits 15rem cards, or a fixed one to six); on a grouped board Fill width fits the columns to the board's width, each growing by an equal share of the spare room or shrinking by its width's share of the shortfall — and tells what a drop into another column changes: status goes through `boardMove`, any other property goes through `updateTask`. Under the Manual sort a card is also dragged to another place inside its status column or across the ungrouped grid, and `boardMove` keeps that place in the project's manual order. Every task is a card, a child too, marked with its parent. Besides the table's fields the board's Display panel offers Sub-task list (everything under the card, each row opening its task, with Add sub-task under the rows — on a card with none too — typing a title into the card and Enter making it a sub-task in To do, [views/board/subtask-list.tsx](views/board/subtask-list.tsx); the Display panel narrows it to the open sub-tasks at any depth, a closed one kept only as the parent of an open one, or to the open children one level down — open being neither done nor canceled), Sub-task stats (the spread over statuses and the share done), Burndown (the open tasks under the card over the board's period, the trend dashed, served by one `taskBurndowns` call per board from the transition log, [analytics/burndown.ts](analytics/burndown.ts)) and Sub-task Gantt (a lane per task under the card: the planned dates outlined, the working statuses it actually stood in — In progress and In review — filled from the transition log, Backlog and To do left out, or both laid over each other, served by one `ganttRows` call per board, [analytics/gantt.ts](analytics/gantt.ts), drawn by [views/analytics/gantt-chart.tsx](views/analytics/gantt-chart.tsx)). The period — a number of days, hours or minutes typed in, 0 for all time by the week — where today stands in it — Right looks back over the past, Center watches the present, half back and half ahead, Left plans ahead, the Gantt drawing the plans and the burndown its dashed trend past a line at today; both charts of a card draw one window by time, so today stands at the same spot in each, in the exact middle when centered ([views/board/chart-window.ts](views/board/chart-window.ts)) — the dates — off, under each chart or once along the card's bottom, few, some or many of them, at round minutes, hours, midnights, Mondays or firsts of a month ([views/board/date-ticks.ts](views/board/date-ticks.ts)) — and what the Gantt shows are picked once per board in the Display panel and kept in the browser apart from the layout ([views/board/chart-preference.ts](views/board/chart-preference.ts)); so are the type sizes of the card's title, description and sub-task list, under Card text ([views/board/card-text-preference.ts](views/board/card-text-preference.ts)); Status, Slug and Sub-tasks — done out of everything under the task — are on both surfaces ([shared/subtree.ts](shared/subtree.ts)). The task key is a field too, Key, shown by default: on the card it stands in a row of chips among the other fields, in the table row it keeps its column left of the title; switching it off takes it away. Description, dragged like any other field, puts the first paragraph of the description on the card (a board that had Show description on before it was a field keeps it on) — headings, code and markup passed over ([shared/first-paragraph.ts](shared/first-paragraph.ts)). The card draws nothing but the fields, in the Display panel's order: Title is a field too — moved like the others, never hidden — and so are what the card once pinned above it, Parent, Slug, Active (the working agents), Worktree (a task read from a thread's worktree), and the Attachments clip. Chips that follow each other share a row, and each full-width field — Title, Description, Sub-task list, Sub-task stats, Burndown, Sub-task Gantt — stands where the panel lists it, splitting the chips around it into a row above and a row below; with every field off the card is its title alone ([views/board/card-sections.ts](views/board/card-sections.ts)). A board set up before Title was a field keeps its look: its old top line — slug as it was, agents, parent, worktree — goes above the title, the clip to the end ([views/common/row-field-preference.ts](views/common/row-field-preference.ts)). A Gantt row names its task on hover — key and title, status, plan Start → Due — and a click on that tooltip opens it; a task's line ends where it was done, marked with the Done icon — a task done without a stretch of work gets the mark alone. A tag on the card and in the rail is filled with its own colour, the text black or white by its lightness ([views/common/label-fill.ts](views/common/label-fill.ts)). A saved view names its `surface`, `table` or `board`; a board view carries its grouping in `board`, and an open one offers Reset and Save once its layout moves off what it saved.

Delegated agent threads are tracked live through bb lifecycle events (`thread.created/active/idle/failed/archived/deleted`) plus a `thread-status-reconcile` background service that recovers transitions missed while the plugin was unloaded ([lifecycle/index.ts](lifecycle/index.ts)); thread live-state is process memory and is deliberately not written back into the task file (see [decisions/tasks-plus-thread-state-is-not-a-file-field.md](decisions/tasks-plus-thread-state-is-not-a-file-field.md)).

# Tasks+ — по-русски

> Форк плагина Tasks: задачи хранятся Markdown-файлами на диске, добавлены нативные поля рабочего процесса — Type, Estimate, Check, время и бюджет.

## Для чего нужен

Tasks+ — трекер в стиле Linear внутри bb (id плагина `tasks-plus`) для планирования работы, делегирования её агентам и связи записи о задаче с тредами, которые её делают. Он переносит всё, что даёт встроенный плагин Tasks — проекты и папки, ключи задач, статусы и приоритеты, метки, подзадачи, Markdown-комментарии, вложения, пресеты агентов и делегирование, упоминания задач и полный CLI `bb tasks`, — и забирает себе имя этого CLI, чтобы заменить встроенный плагин.

Поверх этой базы он добавляет нативные поля для workflow проектной памяти, редактируемые в рейле задачи: **Type** (epic, feature, bugfix, spike, refactor, migration, design), **Estimate** (xs, s, m, l, xl), **Check** (мультивыбор из test, review, design, browser), **Planned Time** и **Actual Time** в целых минутах, **Budget**, **Limit** и **Cost** в долларах с точностью до цента, **Start date** и **Due date** — запланированные начало и окончание работ. Type, Estimate, время, деньги и обе даты допускают пустое значение — задачу можно оставить без них, как `priority = none`.

Эпик — обычная задача типа Epic. Подзадачи вкладываются на любую глубину, а задача входит в эпик, который ближе всех к ней среди предков типа Epic, что бы ни лежало между ними; тип задачи ничего не делает с её детьми. Этого предка доска вычисляет при чтении задач ([shared/epic.ts](shared/epic.ts), `Task.epicId`); его называет `bb tasks show`, а на доске поля Epic нет — место задачи под эпиком читается через Parent; а в эпик задачу кладут, делая эпик её родителем (меню Parent в рейле, `bb tasks update --epic <ключ>`). Старые папки эпиков `<исполнитель>/<эпик>/<статус>/` читаются, пока `bb tasks epics migrate` не превратит каждую в задачу-эпик и не перенесёт её файлы к ней ([filesync/epic-migrate.ts](filesync/epic-migrate.ts)). На доске каждая задача — карточка, дочерняя с отметкой родителя; в меню полей карточки есть Sub-task list — под строками стоит Add sub-task, и у карточки без подзадач тоже: название вводится прямо в карточке, Enter заводит подзадачу в To do; в нём же выбор: все подзадачи, все открытые (закрытая остаётся только родителем открытой) или открытые первого уровня, открытая — не Done и не Canceled, — Sub-task stats, Burndown — открытые потомки за период доски по журналу переходов ([analytics/burndown.ts](analytics/burndown.ts)), и Sub-task Gantt — полоса на каждого потомка: плановые даты контуром, фактические рабочие статусы из журнала — In progress и In review — заливкой, Backlog и To do не рисуются, Done — отметкой или оба сразу ([analytics/gantt.ts](analytics/gantt.ts), [views/analytics/gantt-chart.tsx](views/analytics/gantt-chart.tsx)); период — число дней, часов или минут, 0 — всё время по неделям, — положение «сегодня» в нём — Right смотрит в прошлое, Center следит за текущим, Left планирует вперёд, Гант рисует планы, а Burndown — пунктир тренда за линией «сегодня»; оба графика карточки рисуют одно окно по времени, и «сегодня» стоит у них в одной точке, по центру — ровно посередине ([views/board/chart-window.ts](views/board/chart-window.ts)), — даты — выключены, под каждым графиком или один раз внизу карточки, редко, средне или часто, на круглых минутах, часах, полуночах, понедельниках или первых числах ([views/board/date-ticks.ts](views/board/date-ticks.ts)), — и режим Ганта выбираются один раз на доску в панели Display и хранятся в браузере отдельно от раскладки ([views/board/chart-preference.ts](views/board/chart-preference.ts)), а Status, Slug и Sub-tasks — и в таблице, и на доске. Ключ задачи — тоже поле, Key, включённое по умолчанию: на карточке оно в ряду чипов среди остальных полей, в строке таблицы — в своей колонке слева от заголовка; выключенное пропадает. Description — первое по умолчанию поле списка полей доски, перетаскивается как остальные — выводит на карточке первый абзац описания — без заголовков, кода и разметки ([shared/first-paragraph.ts](shared/first-paragraph.ts)). Под заголовком карточка рисует поля в порядке меню Display: идущие подряд чипы делят один ряд, а каждое поле во всю ширину — Description, Sub-task list, Sub-task stats, Burndown, Sub-task Gantt — встаёт там, где оно стоит в меню, и делит чипы вокруг себя на ряд выше и ряд ниже; скрепка вложений замыкает последний ряд чипов, а у карточки без чипов стоит одна внизу ([views/board/card-sections.ts](views/board/card-sections.ts)). Fill width в разделе Columns подгоняет колонки доски под её ширину: каждая растягивается на равную долю свободного места или сжимается пропорционально своей ширине. Доска без группировки — одна сетка, число её колонок задаёт меню Group: Auto укладывает сколько влезет карточек по 15rem, либо ровно от одной до шести. При сортировке Manual карточку перетаскивают на другое место и внутри колонки статуса, и по сетке без группировки, а `boardMove` запоминает это место в ручном порядке проекта.

Второе принципиальное отличие от оригинала — где живут задачи: задача это Markdown-файл в папке статуса на диске, а не строка в базе. Метаданные доски (папки, пресеты, сохранённые виды) по-прежнему хранятся в хранилище плагина, но сами задачи читаются заново из своих файлов, а каждая правка из панели коммитится и пушится в git-репозиторий доски.

## Как устроено

Фронтенд занимает четыре слота хоста в [app.tsx](app.tsx):

- `app.slots.navPanel` — основная панель **Tasks+** по пути `tasks`, её рисует `TasksAppShell`, с `experimental_sidebarAccessory` (`TasksSidebarAccessory`) в подвале сайдбара. Навигация — колонка этой панели рядом с областью, которой она правит; на узком экране помещается одна, поэтому панель открывается на области, а кнопка топбара приводит навигацию во всю ширину ([shell/columns.ts](shell/columns.ts)).
- `app.slots.threadPanelAction` (id `task`) — вкладка **Task** в правой панели треда (`TaskEmbedPanel`).
- `app.slots.experimental_threadHeaderAction` (id `current-task`) — действие задачи в шапке треда (`CurrentTaskHeaderAction`).
- `app.slots.messageDirective` (id `task`) — рендерит листовую директиву `::task{key="…"}` в сообщении карточкой задачи (`TaskDirectiveCard`).

Бэкенд ([server.ts](server.ts)) собирает store и его модули: `registerTasksApi` (RPC — единственный мост, которым пользуется фронтенд), `registerAttachments`, `registerTasksCli` (CLI `bb tasks`), `registerDelegation`, `registerMentions`, `registerFolders` и `registerLifecycle`. Упоминания регистрируются через `bb.ui.registerMentionProvider` (id `task`, метка **Tasks**): `@` в композере ищет задачи по ключу или заголовку и отдаёт агенту контекст задачи.

Данные берутся с диска, а не из SQL. `createStore` поднимает файловый store, где каждая задача — Markdown-файл в папке статуса (см. [decisions/tasks-files-are-the-store.md](decisions/tasks-files-are-the-store.md) и [decisions/tasks-every-file-in-a-status-folder-is-a-task.md](decisions/tasks-every-file-in-a-status-folder-is-a-task.md)); каждый вызов смотрит на файлы заново, но файл разбирается повторно, только когда изменился его stat ([filesync/parse-cache.ts](filesync/parse-cache.ts)), а вызовы, пришедшие вместе без записи между ними, делят одно чтение доски — поэтому экраны просят доску целиком, а не по задаче: доска и таблица рисуются из `listTasks`, а число вложений и треды всех карточек берут одним вызовом `taskCardMeta`, — а доски, папки, пресеты, сохранённые виды и ручной порядок задач каждого проекта лежат в `bb.storage.kv`. `listTasks` отдаёт задачи проекта в этом ручном порядке — ещё не расставленные первыми, новые сверху, — а `boardMove` переписывает его по соседям сброса карточки ([shared/manual-order.ts](shared/manual-order.ts), [filesync/order-store.ts](filesync/order-store.ts), [docs/decisions/tasks-plus-manual-order-in-plugin-kv.md](../docs/decisions/tasks-plus-manual-order-in-plugin-kv.md)). Поля workflow сериализуются в YAML-frontmatter каждого файла — `type`, `estimate`, `minutes` (Planned Time), `minutes_actual` (Actual Time), `budget`, `limit` и `cost` — модулем [filesync/task-file.ts](filesync/task-file.ts). Старые строки `tokens`, `tokens_actual` и `checks` плагин не читает и не стирает; сохранённый вид, где ещё значится снятое поле `tokens`, отдаётся без него. Блок `flow` (`id`, `name`) пишет не доска, а плагин Flow: этап прогона, отдавший файл задачи результатом, ставит в него flow треда; доска читает блок в `Task.flow`, сама его не пишет, а карточка задачи показывает его ссылкой на страницу flow во Flow ([shared/flow-route.ts](shared/flow-route.ts)).

Делегированные треды агентов отслеживаются вживую через события жизненного цикла bb (`thread.created/active/idle/failed/archived/deleted`) плюс фоновый сервис `thread-status-reconcile`, который восстанавливает переходы, пропущенные пока плагин был выгружен ([lifecycle/index.ts](lifecycle/index.ts)); живое состояние треда держится в памяти процесса и намеренно не пишется обратно в файл задачи (см. [decisions/tasks-plus-thread-state-is-not-a-file-field.md](decisions/tasks-plus-thread-state-is-not-a-file-field.md)).

## Слои

Зависимости идут строго вниз: каждый слой знает только про те, что выше него в таблице.

| Слой | Путь | Ответственность |
| --- | --- | --- |
| Типы | [db/types.ts](db/types.ts) | DTO `Task`/`CreateTaskInput`/`UpdateTaskInput` и enum-массивы полей workflow `TASK_TYPES`, `TASK_ESTIMATES`. Без I/O. |
| Контракт | [shared/contract.ts](shared/contract.ts) | RPC-контракт, zod-схемы и DTO, общие для сервера и приложения; в [shared/format.ts](shared/format.ts) — форматтеры показа, объявленные один раз для всех экранов. |
| Сеть | [remote](remote) | Сетевые стыки доски-базы: клиент Hrana для libSQL и Turso Platform API. Из плагина ничего не импортирует. |
| Файловый store | [filesync](filesync) | Задачи-как-файлы: разбор/сериализация frontmatter, папки статусов, слаги, конфиг доски, патчи, разрешение корней; порт `TaskRepo` с реализациями на папке и на базе. |
| API | [api/index.ts](api/index.ts) | RPC-обработчики поверх файлового store; create/update/get проводят поля workflow; `flow` только читается. |
| Функции | [cli](cli), [delegate](delegate), [mentions](mentions), [folders](folders), [attachments](attachments), [lifecycle](lifecycle), [steer](steer), [threads](threads) | CLI `bb tasks`, делегирование и пресеты, провайдер упоминаний `@`, папки, вложения, отслеживание жизненного цикла тредов, доставка комментариев и живое состояние тредов. |
| Клиент | [client](client) | RPC-хуки и запросы, каналы инвалидации, разбор маршрута и навигация, провайдер рефреша: стык приложения с контрактом, про экраны не знает. |
| Компоненты | [components](components), [editor](editor) | Обёртки дизайн-системы, диалоги, черновик вложений, метаданные задачи (подписи, иконки, состояния тредов и PR в [components/task-meta.tsx](components/task-meta.tsx)) и Markdown-редактор. |
| Экраны | [views](views) | Доска, таблица, деталь (редакторы Type/Estimate/Check, времени и бюджета в [views/detail/rail.tsx](views/detail/rail.tsx)), активность, аналитика — дашборд плиток, каждая — запись настроек [shared/analytics-tile.ts](shared/analytics-tile.ts), на которую отвечает RPC `analyticsTile` ([analytics/tile.ts](analytics/tile.ts)): тип графика, оси, мера, разбивка, переключатель сегмент-контролом, фильтр доски и сортировка по любому полю, а под графиком — таблица задач выбранного сегмента: колонки, сортировка, строки и высота строк хранятся в плитке, задачи по тем же ячейкам отбирает и сортирует RPC `analyticsTileTasks` ([views/analytics/segment-table.tsx](views/analytics/segment-table.tsx)); набор плиток и рядов хранится в KV плагина, правится в боковой панели ([views/analytics/tile-panel.tsx](views/analytics/tile-panel.tsx)) и переставляется за шапку плитки; колонки — срезы День, Неделя, Месяц и Всё время, по неделям от первой задачи, `analyticsSpan`; цвета — в [views/analytics/chart-colors.tsx](views/analytics/chart-colors.tsx): проект — своим цветом из настроек проекта, прочие серии — палитрой, или ступени Reduced Colors из [packages/reduced-colors](../packages/reduced-colors), проекты тоже, если настройка [shared/reduced-projects.ts](shared/reduced-projects.ts) не оставляет им свои; белый и чёрный — с обводкой цветом рамок темы; настройка — своя секция на странице настроек плагина), управление, embed и шапка. |
| Оболочка | [shell](shell), [app.tsx](app.tsx) | Только композиция: нав-панель, сайдбар, топбар и монтаж экранов. |

Точный порядок, включая серверные папки, объявлен один раз в [architecture.test.ts](architecture.test.ts) и охраняется этим тестом через [packages/layer-guard](../packages/layer-guard): импорт вверх, вбок внутри слоя или в папку, которой нет в слоях, роняет прогон.
